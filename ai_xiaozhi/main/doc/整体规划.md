## 1. 结论速览

| 需求 | 结论 | 关键约束 |
|---|---|---|
| 实时门铃展示画面（摄像头画面显示在 2.4" 屏上） | ✅ **可以实现** | 屏幕是 SPI 屏（20MHz），满屏刷新是硬瓶颈：QVGA 实际 7~10fps，SPI 提频到 40MHz 后 12~18fps |
| 监控数据存入 SD 卡（事件录像 / 连续录像） | ✅ **可以实现** | SD 卡座只接了 **1-bit SDIO**（CLK/CMD/D0），无卡检测脚、DAT1~3 全悬空，顺序写约 1~2MB/s，够存 MJPEG |
| 两者同时做（门铃触发→预览+录像） | ✅ **推荐形态** | 帧率取 QVGA@8fps 录像 + 预览抽帧，可与语音链路共存 |
| 与"AI 小智语音聊天"同时满负荷运行 | ⚠️ **不建议** | 语音链路（AFE+opus+WebSocket）已占满 core1 高优先级；建议**模式互斥**（语音模式 ↔ 门铃/监控模式），由按键切换 |
| 新增外部门铃按钮 / PIR 等外设 | ❌ **无空闲 GPIO** | GPIO 已用尽，只能复用现有 ADC 按键网络（改硬件分压）、触摸屏或牺牲 USB(GPIO19/20) |

**总体判断：硬件资源刚好够，软件需要"分阶段、模式互斥"地增量实现，不能把摄像头/录像塞进现有语音任务路径。**

## 2. 硬件能力盘点（来自原理图）

### 2.1 主控与存储

| 项目 | 参数 | 备注 |
|---|---|---|
| 主控 | ESP32-S3FN8（内封 8MB Quad Flash，QFN56） | 无外置 Flash |
| 外部 PSRAM | **ESP-PSRAM64H = 8MB（64Mbit）Quad SPI**，挂在芯片专用 SPI 脚（VDD-SPI/SPIHD/SPIWP/SPICS1/SPICLK/SPIQ/SPID） | 关键：**Quad 模式**。若误配 Octal，会占用 GPIO33~37，摄像头直接不可用 |
| 电源 | USB Type-C 5V → F1 → U9(M3406-ADJ, FB 3MΩ/665kΩ) → 3V3；CN2 为 VBAT 电池接口 | 峰值估算 700mA 以内，5V/1A 适配器够用 |
| 调试 | UART0（GPIO43/44）、USB D±（GPIO19/20） | 两者都被占用，**无法再作普通 IO 之外复用** |

> ⚠️ 仓库里**没有 `sdkconfig`**（只有 `partitions.csv`）。当前能跑说明本机存在一份未纳入版本管理的配置。**M0 阶段第一件事就是把它固化**，否则无法保证后续"PSRAM/Flash 模式/分区表"不被改坏。

### 2.2 外设清单

| # | 器件 | 接口 | 说明 | 代码现状 |
|---|---|---|---|---|
| 1 | ES8311 编解码 + NS4150B 功放 + 模拟 MIC | I2C + I2S | 16kHz/单声道/16bit，PA-EN=GPIO7 | ✅ 已实现 |
| 2 | **OV2640 摄像头**（FPC1） | DVP 8bit 并口 + SCCB(共用 I2C) | D2~D9/PCLK/VSYNC/HREF/MCLK；**RESET 与 PWDN 只有上下拉电阻，无 GPIO**（上电即工作，不可软断电/软复位） | ❌ **未实现**（`main/shoot/` 是空目录） |
| 3 | **Micro SD 卡座**（CARD1） | SDIO **1-bit** | CLK=GPIO14、CMD=GPIO13、D0=GPIO15；DAT1/2/3、CD 全部 NC；CMD/D0 有 10k 上拉 | ❌ **未实现** |
| 4 | ST7789 SPI 屏 320×240（FPC2/LCD1） | SPI + 背光 | 见 2.3；背光仅 GPIO 开关（Q2，可改 PWM 调光） | ✅ 已实现（20MHz，LVGL 16 行双缓冲） |
| 5 | **电容触摸**（GT 系列，CTP FPC2） | I2C + GT-RST + GT-INT | INT=GPIO42，RST=GPIO17 | ❌ **未实现**（硬件具备） |
| 6 | WS2812 ×2（LED2/LED3 级联） | 单总线 | DIN=GPIO46 | ❌ 未实现（可做门铃/录像状态灯） |
| 7 | ADC 按键 SW2 / SW3 | ADC1_CH7 | 同一脚 GPIO8，靠分压区分（0~500mV / 1300~1800mV）；SW1=硬件复位 | ✅ 已实现（单击、长按） |

### 2.3 完整引脚占用表（原理图网表核对结果）

**LCD（SPI2_HOST）**

| 信号 | 网络名 | GPIO | 代码值 |
|---|---|---|---|
| SCLK | SPI1-SCL | 48 ¹ | `EXAMPLE_PIN_NUM_PCLK = 47` ² |
| MOSI | SPI1-MOSI | 47 ¹ | `EXAMPLE_PIN_NUM_DATA0 = 48` ² |
| CS | SPI1-CS | 21 | 21 ✅ |
| DC | LCD-D/C | 45 | 45 ✅ |
| RST | LCD-RESET | 16 | 16 ✅ |
| BL | LCD-BG | 40 | 40 ✅ |
| MISO | SPI1-MISO | 18 | 未用 |

> ¹ 原理图上 SPI1-SCL/MOSI 接在芯片 **pin37(SPICLK_P)/pin36(SPICLK_N)**，这两个脚只有在 flash/PSRAM 为 **Quad** 模式时才可作为 GPIO47/48 使用。
> ² 现有代码把 47 当 SCLK、48 当 MOSI，与原理图网络标号的对应关系**需实测确认一次**（不影响新增功能，但建议在 M0 顺手核对，避免以后换屏或换 IDE 时踩坑）。

**音频**

| 信号 | GPIO |
|---|---|
| I2C SDA / SCL（ES8311 + OV2640 SCCB + 触摸共用） | 0 / 1 |
| I2S MCLK / BCLK / WS / DOUT / DIN | 3 / 2 / 5 / 6 / 4 |
| PA-EN（功放使能） | 7 |

**摄像头 OV2640（12 根，全部为 GPIO）**

| 摄像头信号 | 原理图网络 | GPIO |
|---|---|---|
| D2 / D3 / D4 / D5 | CAM_D2 / D3 / D4 / D5 | 9 / 11 / 12 / 10 |
| D6 / D7 | CAM_D6 / D7 | 33 / 35 |
| D8 / D9 | CAM_D8 / D9 | 36 / 38 |
| PCLK | CAM_PCLK | 34 |
| XCLK(MCLK) | CAM_MCLK | 37 |
| VSYNC | CAM_VSYNC | 41 |
| HREF | CAM_HREF | 39 |
| SIOD / SIOC | I2C_SDA / I2C_SCL | 0 / 1（共用总线） |
| RESET / PWDN | 10k 上拉到 2V8 / 下拉到 GND | **无 GPIO** |

**SD 卡**：CLK=14、CMD=13、D0=15（1-bit，无 CD 脚、无 DAT3 上拉）

**其余**：KEY=8（ADC）、WS2812=46、GT-INT=42、GT-RST=17

**空闲 GPIO 统计**：仅 GPIO19/20（USB D±）与 GPIO43/44（UART0）名义上"空闲"，但它们分别是 USB-Serial-JTAG 与日志串口。**结论：没有可自由支配的 GPIO 去接门铃按钮/PIR/继电器。**

### 2.4 资源余量

| 资源 | 总量 | 语音功能已占 | 门铃+录像预估 | 余量判断 |
|---|---|---|---|---|
| Flash | 8MB | factory 4M + model 500K + nvs 24K ≈ 4.6M | 新代码 +1~2M | ✅ 充裕（分区表剩余约 3.4M 未使用） |
| PSRAM | 8MB | 语音链路约 1.5~2MB（AFE/模型/3×16K ringbuf/opus 缓冲） | 相机 2×150KB + 录像环形 1MB + JPEG 工作区 64KB ≈ 1.4MB | ✅ 充裕 |
| 内部 SRAM | 512KB | WiFi/lwIP ~60KB、LVGL 20KB、I2S DMA、栈 | camera DMA 描述符 ~10KB、FATFS 静态 ~12KB | ⚠️ 偏紧，所有大缓冲必须放 PSRAM |
| CPU | 双核 240MHz | core1 被 AFE feed/fetch + encoder/decoder 占满 | 相机采集/SPI 刷屏/SD 写 | ⚠️ 需把新任务尽量放 core0 且优先级 ≤3 |

### 3.2 现有语音链路（不可破坏）

```
ES8311 MIC ─I2S─> xiaozhi_sr_feed_task ─> AFE ─> xiaozhi_sr_fetch_task ─(VAD=SPEECH & 已唤醒)─> ringbuf_sr2encoder
   └─> xiaozhi_audio_encoder_task ─> ringbuf_encoder2ws ─> xiaozhi_ws_send_audio_task ─wss─> 云端
云端 ─wss(bin)─> ringbuf_ws2decoder ─> xiaozhi_audio_decoder_task ─I2S─> ES8311 喇叭
云端 ─wss(text)─> main.c: process_text_frame ─> LVGL(emoji/text) / iot(SetVolume/SetMute)
```

**对新增功能的三条硬约束（对应项目铁律）**
1. 不改 `xiaozhi_sr.c` / `xiaozhi_audio*.c` / `xiaozhi_ws.c` 的既有路径与优先级；
2. 新功能通过独立模块 + 独立开关（宏）实现，默认关闭也不影响语音；
3. `main.c` 只在初始化区追加一行"模式仲裁初始化"，不重排现有顺序。

### 3.3 可直接复用的既有能力

- `xiaozhi_lcd.c` 里的 `spi_bus_initialize(SPI2_HOST)` + `esp_lcd_panel_draw_bitmap` → 视频帧直刷可直接沿用同一总线与面板句柄（需把 `panel_handle` 暴露，目前已是全局变量 `extern`）；
- `esp_jpeg_decode()` → 把 OV2640 的 JPEG 帧解码上屏（省 PSRAM 带宽的备选方案）；
- `xiaozhi_audio_play()` → 门铃提示音/语音播报直接复用；
- LVGL 的 `screen`/`lv_label` 对象 → 录像中 OSD（时间、"REC"图标）用 LVGL 画最省事。

### 3.4 现状缺口（本次要补的）

| 缺口 | 影响 |
|---|---|
| 无 `sdkconfig` 基线 | 构建不可复现，扩功能风险最高 |
| 无摄像头驱动（`shoot/` 空） | 需求 A/B 的前置 |

## 4. 需求拆解与可行性论证

### 4.1 需求 A：实时门铃展示画面

**目标定义（建议）**：门铃被触发（按键/触摸/网络指令）后，屏幕从"小智表情"切到摄像头实时画面，同时响铃、抓拍一张 JPEG、录像 15~30s，并在结束后回到原界面。

**数据通路**

```
OV2640 ─DVP 8bit─> ESP32-S3 LCD_CAM 外设 ─DMA─> PSRAM 帧缓冲(RGB565 或 JPEG)
        └─> [方案A] 直接 RGB565 ──SPI2──> ST7789  (无解码, 吃 PSRAM 带宽)
            [方案B] JPEG ─esp_jpeg解码─> PSRAM RGB565 ──SPI2──> ST7789 (省 PSRAM 带宽, 吃 CPU)
```

**帧率/带宽预算（1 帧 QVGA 320×240×2B = 153,600 B）**

| 场景 | SPI 时钟 | 单帧传输耗时 | 理论 fps | 预计实测 fps |
|---|---|---|---|---|
| 全屏 RGB565 直刷 | 20MHz（现配置） | 61.4 ms | 16.3 | **6 ~ 10** |
| 全屏 RGB565 直刷 | 40MHz（ST7789 可支持，需实测） | 30.7 ms | 32.6 | **12 ~ 18** |
| 半分辨率 160×120 直刷 + 2× 放大 | 40MHz | ~7.7 ms | 130 | 25 ~ 30（画质差） |
| VGA 640×480 | 40MHz | 122.9 ms | 8.1 | 5 ~ 7（不推荐） |

**结论**：QVGA + 40MHz 是本方案的性能甜点；VGA 不可行（除非改并口屏）。帧率上限来自 SPI 屏本身，不是摄像头（OV2640 QVGA 可出 30fps）。

**关键技术点**
1. 相机帧缓冲必须放 PSRAM，且用 **2 个缓冲轮转**（`fb_count=2`，`CAMERA_GRAB_LATEST`）；
2. **预览绕过 LVGL**：`esp_lcd_panel_draw_bitmap()` 直接刷（LVGL 全屏重绘 320×240 反而更慢），LVGL 只负责 OSD 叠层；
3. 建议把 `EXAMPLE_LCD_PIXEL_CLOCK_HZ` 提到 40MHz，并做 1 次画面完整性验证（花屏则退回 30MHz）；
4. 摄像头 SCCB 与 ES8311 共用 GPIO0/1（详见 7 号风险）；
5. 屏幕旋转/镜像：现有配置为 `swap_xy=true, mirror_x=true`，摄像头画面需要同样处理（必要时软件旋转 90°，QVGA 两次 memcpy 约 3~5ms，可接受）。

### 4.2 需求 B：监控数据存入 SD 卡

**存储通路**：`帧 → 队列(PSRAM) → recorder 任务 → FATFS(f_write, 4~8KB 批量) → SDMMC 1-bit`

**速率预算（1-bit SDIO）**

| 项目 | 数值 |
|---|---|
| SDMMC 1-line @20MHz 理论 | 2.5 MB/s |
| FATFS 顺序写实测（1-bit，常规卡） | **1.0 ~ 2.0 MB/s** |
| QVGA JPEG 单帧（q=12） | 约 12 ~ 25 KB |
| 8 fps 录像码率 | 约 **120 ~ 200 KB/s** |
| 32GB 卡（预留 500MB）连续录像 | 约 **45 小时**（8fps）／约 3 天（4fps） |
| 单次事件录像 20s | 约 3 ~ 4 MB → 32GB 可存约 **7000+ 次事件** |

**三种存储策略（可组合，按需开关）**

| 策略 | 描述 | 空间/功耗 | 适用 |
|---|---|---|---|
| S1 事件抓拍 | 触发时存 1 张 JPEG + 1 条 CSV 事件记录 | 极小 | 必做（成本最低） |
| S2 事件录像 | 触发时录 15~30s MJPEG-AVI | 小 | **推荐主方案** |
| S3 连续录像 | 7×24 循环覆盖，按 5 分钟切片 | 大（约 10GB/天） | 可选，需卡 ≥64GB |

**推荐文件规范**

```
/sdcard/
├─ DCIM/2026-11-05/EVT_20261105_143012_001.avi     # MJPEG-AVI，通用播放器可直接播
├─ DCIM/2026-11-05/SNAP_20261105_143012.jpg        # 事件抓拍
├─ LOG/event.csv                                    # 时间,类型,文件,时长,触发源
└─ CONFIG/recorder.json                             # 策略参数（分辨率/fps/时长/覆盖阈值）
```

**关键技术点**
1. **时间戳**：板子无 RTC → 开机后必须 SNTP 授时（`CST-8`），未授时前用 `boot_xxxx` 序号命名并在日志中标记；
2. **掉电安全**：每 1~2s 或每 1MB `f_sync()`；每个文件独立关闭（切片），避免整卡 FAT 损坏；
3. **循环覆盖**：保留 N 天 + 剩余空间 <500MB 时删最旧文件；删除需串行在 recorder 任务里做；
4. **无卡检测脚**：只能靠"挂载失败/写错误/超时"判断拔卡 → 拔卡后要能自动降级为"只预览不录像"并持续重挂载（每 5s 重试）；
5. **DAT3 未上拉**：个别卡可能识别不了，属硬件风险，遇到再考虑加 10k 上拉（改板）。

### 4.3 与现有语音功能的共存分析

| 冲突面 | 分析 | 对策 |
|---|---|---|
| core1 CPU | AFE feed/fetch + opus 编解码已占满 core1 | 相机/显示/录像任务全部 pin 到 **core0**，优先级 2~4 |
| PSRAM 带宽 | 相机写入 + SPI DMA 读出 + 语音模型访问 | 预览用 2 缓冲最小化拷贝；录像直接读相机 JPEG 缓冲，不额外 memcpy |
| 内部 SRAM | `s_lines`/LVGL 双缓冲在内部 RAM | 视频层复用 `panel_handle`，不再申请新缓冲；必要时临时关闭 LVGL 双缓冲 |
| 音频自激 | `aec_init=false`，门铃/提示音会被 MIC 拾取 → 误唤醒/误 VAD | 响铃期间 `xiaozhi_handle.is_wakeup=false` + 暂停 fetch 送数据，或把响铃放到语音空闲时 |
| 屏幕争用 | LVGL 任务与视频层同时刷屏会撕裂 | 预览期间 `lvgl_port_lock()` 只画 OSD，主画面走直刷；或用独立的"媒体层状态"让 LVGL 隐藏 emoji/text |
| 电源 | 相机 60~120mA + WiFi 峰值 240mA + 背光 + SD 写 | 建议 5V/1.5A 供电；电池模式下降帧率/关预览 |

**结论：做成"三模式仲裁"最稳**
- `MODE_VOICE`（默认，现状）：小智聊天，相机与 SD 全部不初始化（省电、零风险）
- `MODE_DOORBELL`：唤醒→预览+响铃+事件录像，语音链路降到"只监听唤醒词"
- `MODE_MONITOR`：低帧率连续录像，屏幕显示状态与时间

### 4.4 可行性总表

| 子功能 | 可行性 | 依赖 | 风险等级 |
|---|---|---|---|
| OV2640 出图（QVGA RGB565/JPEG） | ✅ | `espressif/esp32-camera` + 12 脚配置 | 低 |
| JPEG 抓拍存 SD | ✅ | `esp_jpeg`（已有）+ FATFS | 低 |
| 屏幕实时预览 10~15fps | ✅ | SPI 提频 | 中（帧率不达预期时降分辨率） |
| 事件录像（MJPEG-AVI） | ✅ | 自写 AVI 封装（约 200 行） | 中 |

### 5.2 模式仲裁（核心设计）

```
        ┌──────────── 按键(SW2) / 触摸 / 网络指令 ────────────┐
        ▼                                                    │
  MODE_VOICE ──切换──> MODE_DOORBELL ──超时/结束──> MODE_VOICE │
     │  ▲                    │                                │
     │  └──── MODE_MONITOR ◄─┘（可选：无人时进入低帧率录像）    │
     └───────────────────────────────────────────────────────┘
```

- 切换动作 = `xiaozhi_appmode_request(mode)`，由**主控任务串行执行**（不在 ISR/回调里直接初始化外设）；
- 进入 `MODE_DOORBELL` 才 `xiaozhi_camera_init()` + `xiaozhi_sdcard_mount()`；
- 退出时 `xiaozhi_camera_deinit()`（释放 PSRAM）+ `xiaozhi_sdcard_unmount()`，回到语音模式时内存/带宽完全归还；
- 用一个宏 `APP_DOORBELL_ENABLE`（默认 1）/`APP_MONITOR_ENABLE`（默认 0）做功能开关，关掉即等同于现在的固件。

### 5.4 内存预算（PSRAM 8MB）

| 用途 | 大小 | 位置 |
|---|---|---|
| 现有语音链路（AFE/模型/opus/3 ringbuf） | ≈1.5 ~ 2.0 MB | PSRAM |
| 相机帧缓冲 ×2（QVGA RGB565） | 300 KB | PSRAM（`fb_location = CAMERA_FB_IN_PSRAM`） |
| 录像队列（8 帧 JPEG） | ≈200 KB | PSRAM |

| FATFS + VFS + SDMMC | ≈20 KB | 内部 |

峰值占用约 2.7MB / 8MB，**余量充足**。

### 8.1 决策记录（2026-11-05 用户确认）

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 模式策略 | 接受"语音 / 门铃 / 监控"三者互斥；**三个模式均可语音切换**（iot `Mode.SetMode`），并支持按键切换（SW2/SW3 单击） |

#### 8.5.1 关键难点：SCCB 与 ES8311 共用 GPIO0/1

本板 OV2640 的 SIOD/SIOC 与 ES8311 走同一对引脚，而音频链路用的是 `driver/i2c_master`
**新驱动**。esp32-camera 2.1.8 在 IDF < 5.4 时默认编译 `driver/sccb.c`（legacy I2C 驱动），存在两个硬冲突：

1. legacy 驱动与新驱动同时链接时，启动阶段 `check_i2c_driver_conflict()` 会直接 `abort()`
   （`CONFIG_I2C_SKIP_LEGACY_CONFLICT_CHECK` 关闭时）；
2. 两套驱动抢同一组引脚，谁后初始化谁拿走 GPIO 复用，另一方通信全废。

**解决方式**（无需改 sdkconfig 的 I2C 设置，也不产生 abort 风险）：

- 让 esp32-camera 走 **`driver/sccb-ng.c`**（新驱动版 SCCB）。它支持“复用已创建的 I2C 总线”：
  配置 `pin_sccb_sda = -1` + `sccb_i2c_port = 0` 时，内部用 `i2c_master_get_bus_handle(0)` 拿到
  `xiaozhi_audio.c` 建好的总线，并在其上注册 OV2640 设备（0x30）。
- 组件自带的 CMake 只在 IDF ≥ 5.4 才选 `sccb-ng.c`，但 `i2c_master_get_bus_handle()` 在 **IDF 5.3 已存在**，
  因此在根 `CMakeLists.txt` 里把该组件的源文件从 `sccb.c` 换成 `sccb-ng.c`（幂等，升级 IDF 5.4+ 后自动失效）。
- `sccb-ng.c` 有一句 `#include "esp_private/i2c_platform.h"`，该私有头 5.4 才有且实际未被使用；
  用 `main/camera/compat/esp_private/i2c_platform.h` 空占位头补齐。

> 由此带来的**初始化顺序约束**：必须先 `xiaozhi_audio_init()`（建总线）再 `xiaozhi_camera_init()`。
> 好处是摄像头 `deinit` 不会影响 ES8311（SCCB 只摘设备，不删总线），运行期可自由切换像素格式。

### 8.6 修复（语音口令切模式失效，2026-11-05）

**现象**：说“切换到监控模式/门铃模式”时设备不切模式，界面标题不变。

**原因排查**（三处都可能是断点，本次一并加固）：

1. **云端不下发 `Mode.SetMode`**：描述文字只有英文、且没有举例中文说法，大模型容易只回一句“好的”，
   于是设备端 `strcmp(method,"SetMode")` 分支根本进不去（最常见）。
2. **`main.c` 的 iot 分支缺空指针保护**：`commands` 缺失（例如云端下发的 `type=iot` 是 states/状态同步帧）时
   `cJSON_GetObjectItem(cmdItem,"method")->valuestring` 会解引用 NULL，直接崩溃重启；
   同时 `root` 从未 `cJSON_Delete`，每帧泄漏一次 JSON 树。
3. **方法名可能带命名空间**：部分服务端下发 `"method":"Mode.SetMode"`。现在两种写法都接受。

**改动**：

- `main/vol_iot_desc/iot_desc.json`：`Mode` / `SetMode` / 参数说明改为中文并直接举例
  “切换到监控模式/进入门铃模式/回到语音模式/切换模式”，提高大模型调用命中率（描述符结构未变）。
- `main/main.c`：
  - `type` 缺失时告警返回；iot 分支对 `commands`/`method`/`parameters`/`volume` 全部判空，
    未知方法打印 `unknown iot method: xxx`，`SetMode` + `Mode.SetMode` 都接受；
  - 新增 `type=="stt"` 分支：把 ASR 文本交给 `xiaozhi_appmode_voice_text()` 本地兜底；
  - 帧处理结束 `cJSON_Delete(root)`（修泄漏）。
- `main/app/xiaozhi_appmode.c/.h`：新增 `xiaozhi_appmode_voice_text()`（纯本地关键词匹配，
  必须带动作词“切换/进入/打开/关闭/回到/退出/模式”才生效，避免聊天中提到“监控/门铃”就误切），
  支持“下一个/下个模式”循环切；开关 `XIAOZHI_APPMODE_STT_FALLBACK`（默认 1）。
- `main/internet/xiaozhi_ws.c`：`xiaozhi_ws_send_iot_desc()` 增加 `send iot desc, len=xxx` 日志，
  用于确认描述符确实在 hello 之后发出。

**验证方法**：串口看三条日志确认链路走到哪一环——
`send iot desc, len=...`（固件已带 Mode 描述符）→ 说口令后 `Received text data, data: {"type":"iot"...}`（云端下发）
或 `Received text data, data: {"type":"stt"...}`（走本地兜底）→ `[appmode] voice-text: "..." -> monitor` /
`[appmode] voice: mode voice -> monitor` → `[appmode] mode: voice -> monitor (src=voice)`。
若第一条有、第二条完全没有，说明云端没触发任何帧，属服务端/模型侧问题，本地兜底也无法接管。
编译：`idf.py build` 通过（0 error，无新增 warning）。

#### 8.14.2 关键设计

- **取帧不抢摄像头**：摄像头只有一个消费者。监控模式下录像通过 camview 的帧订阅拿到
  同一帧（零额外 `camera_grab`），因此**预览仍是 10fps**；门铃模式没有预览，
  录像任务自己 `xiaozhi_camera_init()` + `grab`，录完立即 `deinit` 归还 PSRAM。
- **AVI 结构**（224 字节头 + `00dc` 块 + `idx1` 索引）：
  `RIFF/AVI ` → `LIST hdrl`（`avih` + `LIST strl`(`strh`/`strf`)）→ `LIST movi` → `idx1`。
  偏移由源文件常量 `AVI_*_POS` 固定，已用脚本逐项核对（头长 224、hdrl 192、strl 116、
  movi base 220），`idx1` 的 offset 以 'movi' 四字符码为基准（首帧 = 4）。
- **掉电安全**：每 `XIAOZHI_REC_SYNC_MS`(1000ms) 回填一次 RIFF/movi 长度、帧数、宽高并 `fsync`，
  关闭时再补 `idx1` 并把 `dwFlags` 置 `AVIF_HASINDEX`。运行期 `dwFlags=0`（还没有索引），
  即使掉电，已落盘的帧也能被播放器按顺序读出。
- **切片**：`XIAOZHI_REC_SLICE_MS=180000`（3 分钟，符合"单文件最长 3 分钟"），
  到点关文件 → 下一轮开新片，每片独立关闭，避免大文件写坏全丢。
- **循环覆盖**：每次开新片前比较剩余空间与保留水位（`XIAOZHI_REC_KEEP_FREE_BYTES=500MB`；
  小卡自动缩到容量 1/4），不足则 `xiaozhi_sdcard_reclaim()` 删 DCIM 里最旧的文件
  （只动 DCIM，不碰 LOG/CONFIG），因此稳态每片只删 1~2 个文件，不会一次性大删。
- **卡满保护**：回收后仍 < `XIAOZHI_REC_MIN_FREE_BYTES`(16MB) → 状态 `no_space`，
  暂停写盘并每 5s 重试；录像期间每 5s 巡检一次空间，低于硬阈值立即切下一片。
- **掉盘降级**：任何 `fopen/fwrite/fsync` 失败 → 关文件（尽力收尾）→ 主动
  `xiaozhi_sdcard_unmount()` 让 `sd_monitor` 走"拔卡重挂载"流程 → 状态 `no_sd`，
  卡回来后自动续录；画面/语音/网页全程不受影响。
- **空文件清理**：一帧都没写进去的切片（开片后立即停/立即掉盘）会被删除，不留垃圾文件。

- **只在监控模式有视频**：其它模式返回 503 并提示"请先切到监控模式"，不抢语音链路资源；

### 8.16 已修复（M6 验收中暴露的两个阻塞问题，2026-11-06，用户实机确认）

**(1) `httpd_start` 失败 `ESP_ERR_HTTPD_TASK` —— 网页整个起不来**

- 现场日志：`[http] httpd_start failed: ESP_ERR_HTTPD_TASK`。
- 定位：SR/音频初始化后，内部 RAM 最大连续块只有 ~7KB（日志 `internal free=20 KB (largest=7 KB)`），
  而 httpd 栈固定要 8192 → `heap_caps_malloc` 失败；且 `httpd_start` 失败会残留监听 socket，
  同进程内重试会 `httpd_server_init: error in listen (112)`（EADDRINUSE），**不能靠重试补救**。
- 修法（`internet/xiaozhi_http.c/.h`）：
  1. `http_stream` 任务栈改放 PSRAM（`xTaskCreatePinnedToCoreWithCaps(..., MALLOC_CAP_SPIRAM)`，
     失败自动回落内部 RAM），把内部 RAM 让给 httpd；
  2. httpd 栈改为**单次创建**：`min(XIAOZHI_HTTP_STACK, 内部最大连续块-1KB)`，下限 4096；
  3. 新增 `heap@...` 内存诊断日志（打印 internal free/largest 与 psram free）。
- 实测日志：`[http] stream task stack in PSRAM (5120 B)` → `[http] heap@httpd_start: ... largest=7 KB`
  → `[http] httpd started with stack=6144 B` → `[http] init ok`。

**(2) 二次切监控模式失败 —— 摄像头 SCCB 重新探测超时**

- 现场现象与日志：复位后第一次切监控正常；切走后再次切监控失败：
  `cam init ok` → 多条 `i2c.master: I2C hardware timeout detected` / `probe device timeout`
  → `camera: Detected camera not supported.` → `Camera probe failed with error 0x106(ESP_ERR_NOT_SUPPORTED)`。
- 根因：本板 OV2640 的 `PWDN`/`RESET` 均为 `-1`（`camera/xiaozhi_camera_pins.h`，硬件固定、无 GPIO 控制）。
  退出监控时 `xiaozhi_camera_deinit()` → `esp_camera_deinit()` 停掉 XCLK，传感器没有硬复位手段；
  再次 `esp_camera_init()` 重走 `SCCB_Probe`（`sccb-ng.c` → `i2c_master_probe`）时传感器不应答，
  只有整机复位才能恢复（故表现为"只能切一次"）。
- 修法（新增开关 `XIAOZHI_CAM_KEEP_INIT`，默认 1，定义在 `camera/xiaozhi_camera.h`）：
  摄像头**只在首次进入监控模式时初始化一次，之后不再 deinit**，退出监控/门铃事件录像结束都只关预览视图；
  影响点三处：`camview_mode_monitor_exit()`、`camview_mode_monitor_enter()` 的 open 失败分支、
  `rec_release_resources()`（均用 `#if !XIAOZHI_CAM_KEEP_INIT` 包住 deinit）。
- 代价：摄像头常驻初始化（PSRAM 约 30KB，实测 init 前后 986→956KB）；非监控模式下无取帧者，
  驱动填满 2 个帧缓冲后停下，不影响语音链路。置 `XIAOZHI_CAM_KEEP_INIT=0` 可回旧行为（本板会再次只能切一次）。
- 验收：用户实机确认「二次切换不闪退」，第一次 `monitor exit: keep camera initialized (XIAOZHI_CAM_KEEP_INIT=1)`。

### 8.17 SD 卡挂载失败 `mount_to_vfs failed (0xffffffff)` 的定位与加固（2026-11-06）

**现场日志**
```
W (154812) vfs_fat_sdmmc: failed to mount card (1)
E (154820) vfs_fat_sdmmc: mount_to_vfs failed (0xffffffff).
I (154827) gpio: GPIO[14]| InputEn: 0| OutputEn: 0| OpenDrain: 0| Pullup: 1| ...
```
**判读（三段对应同一件事）**
| 日志 | 含义 |
|---|---|
| `failed to mount card (1)` | FATFS `f_mount` 返回 FRESULT=**1 = FR_DISK_ERR**，即读引导扇区时**扇区 I/O 失败**（不是 `13 = FR_NO_FILESYSTEM`，所以不是"格式不对"；也不是 `3 = FR_NOT_READY`，不是"没插卡"） |
| `mount_to_vfs failed (0xffffffff)` | 0xffffffff = `ESP_FAIL`，是 `esp_vfs_fat_sdmmc_mount()` 的统一失败返回；**上一条才是真因** |
| `gpio: GPIO[14] ... Pullup: 1` | 失败后 IDF 清理时 `sdmmc_host_deinit_slot()` → `gpio_reset_pin(CLK/CMD/D0)`（`esp_driver_sdmmc/src/sdmmc_host.c:795`），GPIO14=SD CLK，属**预期**，不是别的模块抢引脚 |

- 关键推论：失败发生在 `sdmmc_card_init()` **之后**（`vfs_fat_sdmmc.c` 里先 card_init 才 mount_to_vfs），
  说明 **400kHz 识别阶段是通过的、卡在位且应答正常**，问题出在升到 20MHz 后读扇区。
  典型成因是卡座接触/走线/供电导致的信号完整性余量不足，或卡被热拔后处于异常态。
- 加固（`storage/xiaozhi_sdcard.c`，新增宏 `XIAOZHI_SD_FREQ_FALLBACK` 默认 1）：
  1. 时钟档位 20MHz → 10MHz → 5MHz（`XIAOZHI_SD_FREQ_MIN_KHZ`），**每次失败降一档**；
  2. `sd_monitor` 检测到"刚降档"时不再等满 5s，只等 300ms 就重试，卡在 20MHz 不稳时约 1s 内挂上；
  3. 成功后**记住该档位**（日志 `clock=10000 kHz (fallback clock)`），后续重挂载直接用它；
     `unmount()`/拔卡后档位复位到最高档，重新插卡再按阶梯探一次；
  4. 已在最低档仍失败时按原策略节流（首次 + 每 12 次），并提示查接触/FAT32。
  置 `XIAOZHI_SD_FREQ_FALLBACK=0` 可回旧行为（固定 `XIAOZHI_SD_FREQ_KHZ` 一档）。
- 注意：`format_if_mount_failed` 仍是 `XIAOZHI_SD_FORMAT_IF_FAIL=0`（默认不格式化）——
  FR_DISK_ERR 不是文件系统损坏，格式化**无助于**此类失败，别为此打开。

## 附录 D：术语

- **MJPEG-AVI**：把连续 JPEG 帧按 AVI 容器封装，PC/手机播放器可直接播放，无需转码。
- **DVP**：8 位并行摄像头接口（PCLK/VSYNC/HREF/D0~D7）。
- **OSD**：叠加在视频画面上的文字/图标层（时间、REC）。
- **模式互斥**：同一时刻只有一条主业务链路持有摄像头、SD 与大块 PSRAM。
